# ADR-006. Автентифікація водіїв: OAuth2/OIDC + прив'язка пристрою + MFA

- **Статус:** Accepted
- **Дата:** 2026-10-26

## Контекст

Фейковий або підмінений водій — пряма загроза життю пасажира і ліцензії RideHub; крім того, водій має доступ до персональних даних пасажирів і до грошових операцій (баланс, виплати). Типові атаки: викрадений OTP, SIM-swap, передача акаунта іншій особі, вхід з емулятора. Пасажири автентифікуються простіше (OTP, US-01), бо ризик там нижчий.

## Рушії рішення

- ASR-05 — 100 % входів із неприв'язаних пристроїв потребують повторної перевірки; реакція служби безпеки ≤ 15 хв
- NFR-08 — 2 фактори (OTP + прив'язаний пристрій); повторне селфі ≥ 1 раз на 7 днів; 0 водіїв на лінії без перевірених документів
- NFR-10 — незмінний журнал аудиту
- US-14 — онбординг через «Дію»

## Розглянуті альтернативи

1. **Тільки пароль.** Слабкий: фішинг, повторне використання, передача іншій особі.
2. **Лише SMS-OTP.** Відповідає US-01 для пасажира, але для водія недостатньо: SIM-swap, перехоплення.
3. **Власний сервіс автентифікації в кожному сервісі.** Дублювання, ризик помилок у криптографії, немає єдиної точки відкликання доступу.
4. **Keycloak (OAuth2/OIDC) + MFA (OTP + прив'язка пристрою) + періодична перевірка liveness.** Обрано.

## Рішення

- **Identity Service (CT-05) на Keycloak**, OAuth2/OIDC. Gateway перевіряє JWT за JWKS, сервіси довіряють Gateway і перевіряють ролі та scope.
- **Фактор 1 — OTP** на номер телефону.
- **Фактор 2 — прив'язаний пристрій.** При першому вході після онбордингу застосунок генерує ключову пару у Keychain / Android Keystore; публічний ключ реєструється в Identity. Подальші входи підписують challenge приватним ключем. Новий пристрій = повторна перевірка (OTP + селфі) і сповіщення водію та службі безпеки.
- **Liveness-перевірка** (селфі) щонайменше раз на 7 днів і при вході з нового пристрою.
- **Короткоживучі access-токени** з ролями (RBAC: `driver`, `dispatcher`, `admin`, `partner`) і `device_id`; refresh-токен прив'язаний до пристрою. Значення часу життя підлягають погодженню зі службою безпеки.
- **Онбординг** (US-14): документи з «Дії» за згодою; невдала автоперевірка → ручна. Статус `Driver.verificationStatus` ≠ `VERIFIED` не дозволяє вийти на лінію.
- **Аудит:** вхід, зміна пристрою, відмови, ручні рішення пишуться в append-only журнал.
- **Пасажир:** лише OTP (US-01) з блокуванням після 5 невдалих спроб; платежі захищені 3-D Secure на стороні PSP.

## Наслідки

**Позитивні:**
- Викрадений OTP без пристрою не дає входу; передача акаунта відсікається періодичним liveness.
- Єдина точка керування доступом і відкликання сесій; стандартні протоколи й бібліотеки.
- Keycloak знімає необхідність писати власну криптографію.

**Негативні / ризики:**
- Додаткове тертя для водіїв (селфі, повторна прив'язка при заміні телефону) → ризик відтоку. Мітигація: селфі раз на 7 днів, швидкий процес заміни пристрою через підтримку.
- Прив'язка пристрою не захищає від рутованих пристроїв і емуляторів без attestation (Play Integrity / App Attest); це розглядається в STRIDE (крок 9).
- Keycloak — критична залежність: вхід без нього неможливий. Мітигація: кластер, короткі токени перевіряються Gateway локально за кешованим JWKS, тож уже авторизовані сесії переживають коротку недоступність.
- Операційні витрати на Keycloak (оновлення, налаштування).
