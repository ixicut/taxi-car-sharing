# ADR-007. Адаптери (GoF Adapter) для інтеграції зовнішніх систем і партнерів

- **Статус:** Accepted
- **Дата:** 2026-10-26

## Контекст

RideHub — чистий агрегатор: його ринок дорівнює кількості підключених партнерів, а критичні функції залежать від зовнішніх API з різними протоколами, моделями даних і надійністю: PSP (LiqPay, WayForPay), картографічні сервіси (Google Maps, Visicom), телематика операторів каршерингу, системи таксопарків, KYC, провайдери сповіщень. Якщо чужі моделі просочуються в ядро, кожна інтеграція стає дорогою й ризикованою.

## Рушії рішення

- ASR-06 — новий партнер ≤ 2 тижні, 0 змін у ядрі (NFR-11)
- NFR-05 — перемикання на резервний картографічний сервіс за ≤ 30 с
- ASR-03 — заміна PSP не повинна зачіпати Trip
- NFR-12 — зміна адаптера не вимагає релізу інших сервісів

## Розглянуті альтернативи

1. **Прямі виклики SDK/API партнерів з бізнес-логіки.** Швидко на початку; але чужа модель даних у ядрі, заміна провайдера означає переписування, тестувати можна лише проти реального API.
2. **Універсальна інтеграційна платформа / ESB.** Централізує маппінг, але додає єдину точку відмови й вузьке місце (див. оцінку SOA в ADR-001) і потребує окремої експертизи.
3. **Окремий мікросервіс на кожного партнера.** Максимальна ізоляція, але занадто багато контейнерів для команди з двох осіб і зайвий мережевий стрибок.
4. **Патерн Adapter за стабільним внутрішнім інтерфейсом (антикорупційний шар) всередині сервісу-власника.** Обрано.

## Рішення

Кожен сервіс-власник контексту визначає **стабільний внутрішній інтерфейс** мовою свого домену й тримає всередині адаптери до конкретних зовнішніх систем:

| Інтерфейс (порт) | Власник | Адаптери | Примітка |
|---|---|---|---|
| `PaymentGateway` (`IPaymentGateway`) | Payment Service | `LiqPayAdapter`, `WayForPayAdapter` | Захист CB + Retry (ADR-005) обгортає порт |
| `MapProvider` (`IMapProvider`) | Trip Service, Location Service | `GoogleMapsAdapter`, `VisicomAdapter` | Failover-декоратор перемикає провайдера; спільна невелика бібліотека без бізнес-логіки |
| `TelematicsClient` (`ITelematics`) | Carsharing Service | адаптер на кожного оператора (REST / MQTT) | Конфігурація партнерів — дані, не код |
| `FleetApi` | Carsharing Service | адаптер на систему таксопарку | Також REST-кабінет через Gateway |
| `KycProvider` (`IKycProvider`) | Identity Service | `DiiaAdapter` | |
| `PushGateway` (`IPushGateway`) | Notification Service | `FcmAdapter`, `ApnsAdapter`, `SmsAdapter` | |

Правила: адаптер перетворює чужу модель на внутрішню й не пропускає чужих типів за межі; ядро залежить лише від порту; нового партнера підключають реалізацією порту й конфігурацією. Деталі рефакторингу God Object → Strategy, Observer, Adapter — у кроці 8.

## Наслідки

**Позитивні:**
- Підключення партнера не змінює Trip, Pricing, Matching (NFR-11).
- Заміна або одночасне використання PSP і карт без змін у ядрі; failover картографічного провайдера.
- Контрактні тести і заглушки (stub) замість реальних API — швидші й дешевші тести та chaos-тести (FF-4).

**Негативні / ризики:**
- Додатковий шар і маппінг моделей: більше коду і ризик втрати семантики чужого API («найменший спільний знаменник»).
- Інтерфейс може виявитися надто вузьким для унікальних функцій провайдера; його доводиться розширювати обережно.
- Спільна бібліотека `MapProvider` у двох сервісах створює зв'язність версій; тримаємо її мінімальною й без бізнес-логіки (дозволено FF-3).
- Адаптери партнерів у Carsharing Service збільшують його кодову базу; якщо кількість партнерів різко зросте, адаптери варто виокремити в окремі сервіси.
