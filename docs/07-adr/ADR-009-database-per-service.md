# ADR-009. Database-per-service

- **Статус:** Accepted
- **Дата:** 2026-10-26

## Контекст

ADR-001 обрав мікросервіси. Найпоширеніший спосіб отримати Distributed Monolith — розділити код на сервіси, але залишити спільну БД: зміна схеми зачіпає всі сервіси, масштабування й розгортання знову зв'язані. Паралельно платіжні дані мають окремі вимоги безпеки (PCI DSS, мінімізація області).

## Рушії рішення

- NFR-12 — незалежне розгортання сервісів
- ASR-02 — незалежне масштабування (геоіндекс у Redis, транзакційні дані в PostgreSQL)
- ASR-05, NFR-09 — ізоляція платіжних і персональних даних
- ASR-06 — зміни моделі партнера не зачіпають решту

## Розглянуті альтернативи

1. **Спільна БД і спільна схема.** Прості JOIN і транзакції, але сильна зв'язність, спільні блокування, неможлива незалежна зміна схем. Це Distributed Monolith.
2. **Спільний інстанс, окрема схема на сервіс.** Компроміс: логічна ізоляція при низькій вартості. Фізично одна точка відмови й спільні ресурси.
3. **Окреме сховище на сервіс, жодного прямого доступу до чужих даних.** Обрано.

## Рішення

Кожен сервіс володіє власним сховищем і є єдиним, хто читає або пише в нього:

| Сервіс | Сховище |
|---|---|
| Identity | PostgreSQL |
| Trip | PostgreSQL (поїздки, `saga_state`, outbox) |
| Matching | Redis (стан пропозицій, доступність) |
| Location | Redis GEO |
| Pricing | PostgreSQL |
| Payment | PostgreSQL (платежі, баланси, outbox) |
| Carsharing | PostgreSQL |
| Notification | без власної БД (стан у Kafka і провайдерах) |

- Між контекстами сутності посилаються за ідентифікатором (`TaxiTrip.driverId`), не за зовнішнім ключем.
- Дані чужого контексту — лише через API або події; локальні копії (read model) оновлюються подіями.
- У продакшені — окремий інстанс або кластер на сервіс; Payment — обов'язково окремий. На навчальному стенді допускається один інстанс з окремими схемами й окремими обліковими записами, які не мають доступу до чужих схем.
- Перевіряється автоматично: **FF-03** (крок 9) падає, якщо сервіс звертається до чужої БД.

## Наслідки

**Позитивні:**
- Сервіси еволюціонують і розгортаються незалежно; зміна схеми не ламає чужих.
- Для кожного сервісу обрано оптимальну технологію (Redis для геоіндексу, PostgreSQL для транзакцій).
- Платіжний контур ізольований, область PCI DSS мінімальна.

**Негативні / ризики:**
- Немає JOIN і транзакцій між сервісами: потрібні Saga (ADR-002) і read model.
- Звітність, що поєднує дані кількох контекстів, будується з потоку подій; не можна написати один SQL-запит.
- Дублювання даних (read model) і ризик їхнього розходження; мітигація: події — єдине джерело оновлень.
- Більше інфраструктури для резервного копіювання, моніторингу й міграцій.
