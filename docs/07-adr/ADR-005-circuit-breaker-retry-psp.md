# ADR-005. Circuit Breaker + Retry з експоненційною затримкою для виклику PSP

- **Статус:** Accepted
- **Дата:** 2026-10-26

## Контекст

Payment Service викликає PSP синхронно (hold, capture, release, refund). Це єдина зовнішня залежність, яка одночасно стоїть на критичному шляху замовлення, працює з грошима і не підконтрольна нам. Без захисту завислий PSP вичерпує потоки Payment Service, Trip чекає gRPC-deadline, і зупиняється все замовлення поїздок (каскадна відмова).

## Рушії рішення

- ASR-03 — PSP недоступний 10 хв: 0 скасованих поїздок, відкладені платежі проведено ≤ 30 хв після відновлення
- NFR-05 — відмова PSP не блокує створення і завершення поїздки
- NFR-07 — 0 подвійних списань (повтор має бути безпечним)
- Бюджет gRPC-виклику Trip → Payment — 5 с

## Розглянуті альтернативи

1. **Лише таймаути.** Не запобігають лавині запитів до PSP, що лежить.
2. **Лише Retry.** Посилює навантаження на недоступний PSP, підвищує затримку для користувача, без ідемпотентності небезпечний.
3. **Усі виклики PSP асинхронні через чергу.** Надійно, але результат hold потрібен пасажиру відразу (402 при відхиленні), тому для hold це неприйнятно. Асинхронний шлях залишаємо як fallback.
4. **Retry на рівні service mesh.** Mesh не знає про ідемпотентні ключі та бізнес-відмови (402), тому повторює без урахування семантики. Відхилено.
5. **Circuit Breaker + Retry з експоненційною затримкою та jitter у коді Payment Service.** Обрано.

## Рішення

Композиція `Retry ( CircuitBreaker ( Bulkhead ( TimeLimiter ( виклик PSP ) ) ) )` (Resilience4j).

**Circuit Breaker «psp»:** `slidingWindowType=COUNT_BASED`, `slidingWindowSize=20`, `minimumNumberOfCalls=10`, `failureRateThreshold=50 %`, `slowCallDurationThreshold=1 с`, `slowCallRateThreshold=60 %`, `waitDurationInOpenState=30 с`, `permittedNumberOfCallsInHalfOpenState=3`. Рахуємо таймаути, `IOException`, 5xx, 429; **не** рахуємо 402 та інші 4xx (бізнес-відмова — PSP справний).

**Retry, два профілі:**

| | interactive (hold, release) | background (capture, refund) |
|---|---|---|
| Спроби | 3 | 5 |
| Затримка | 200 мс × 2ⁿ, макс. 1 с | 500 мс × 2ⁿ, макс. 8 с |
| Jitter | ± 20 % | ± 20 % |
| Таймаут виклику | 1,2 с | 3 с |
| Найгірший час | ≈ 4,3 с (< 5 с) | ≈ 24 с |

Повторюємо лише таймаут, помилку з'єднання, 5xx, 429; не повторюємо 4xx і `CallNotPermittedException` (CB відкритий). Усі повтори — з ідемпотентним ключем (ADR-002).

**Fallback:** `PENDING_RETRY`, поїздка продовжується; після вичерпання фонових спроб — `payment.failed` і бізнес-повтори T-18 (5 хв … 24 год).

## Наслідки

**Позитивні:**
- Відмова PSP не зупиняє замовлення поїздок; потоки Payment Service не вичерпуються (bulkhead).
- Jitter запобігає «thundering herd» при відновленні PSP.
- Повтор після таймауту не створює другого списання.

**Негативні / ризики:**
- Параметри (вікно 20, поріг 50 %, 30 с) — стартові оцінки для реальної поведінки PSP; їх треба налаштовувати за метриками після запуску.
- Можливі хибні спрацьовування CB у пік через повільні, але успішні відповіді; мітигація: `slowCallRateThreshold` окремо від помилок і алерт при переході в `OPEN`.
- Два профілі й кілька рівнів повторів (технічний і бізнесовий) ускладнюють тестування; перевіряється chaos-тестом FF-4 (крок 9).
- Прийнятий ризик боргу при `PENDING_RETRY` (ADR-002).
