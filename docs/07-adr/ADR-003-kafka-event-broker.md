# ADR-003. Apache Kafka як брокер подій

- **Статус:** Accepted
- **Дата:** 2026-10-26

## Контекст

Після ADR-001 і ADR-002 усі асинхронні взаємодії йдуть через брокер: геопотік (`driver.location.updated`), команди й відповіді пошуку водія (`trip.search.requested`, `driver.assigned`), статуси поїздки (`trip.status.changed`), результати платежів, Outbox-публікація. Брокер стає критичною інфраструктурою.

## Рушії рішення

- ASR-01 — потік до ≈ 8 300 повідомлень/с, кілька споживачів
- ASR-02 — буфер для сплесків (50 замовлень/с)
- ASR-04 — порядок подій однієї поїздки; надійність доставки (Outbox)
- NFR-05, ASR-03 — повільний або недоступний споживач не зупиняє виробника
- NFR-13 — діагностика й відтворення подій

## Розглянуті альтернативи

1. **RabbitMQ.** Гнучка маршрутизація, пріоритети, TTL повідомлень, простий для задач-черг. Але повідомлення видаляється після споживання: немає повторного читання історії; порядок гарантовано лише в межах однієї черги, а для fan-out потрібні окремі черги на кожного споживача. Ми використовуємо переважно потоки подій, не черги задач.
2. **Redis Streams.** Уже є Redis у стеку, низька затримка. Але менш зрілі споживчі групи, менші гарантії довговічності, масштабування й операційний досвід гірші; брокер подій для грошей не варто будувати на інструменті кешу.
3. **Apache Kafka.** Партиціонований журнал подій із retention.

## Рішення

Обираємо **Apache Kafka**.

- Ключ партиції = `tripId` для подій поїздки (порядок і ідемпотентна обробка, ADR-002); для геопотоку — ключ = геозона міста (шардування, ASR-01).
- Retention: 24 год для геопотоку; довше для бізнес-подій (за потреби повторної обробки).
- Окрема consumer group на кожен сервіс-споживач: Notification, Matching, Location і Payment читають незалежно один від одного.
- Семантика доставки **at-least-once**; ідемпотентність — на стороні споживачів.
- Топіки перелічено в [розділі 4.4](../04-architecture-style-c4.md#основні-топіки-kafka).

Throughput не є вирішальним чинником: 8 300 повідомлень/с витримали б усі три варіанти. Вирішальні — повторне читання історії, порядок за ключем і fan-out через consumer groups.

## Наслідки

**Позитивні:**
- Нових споживачів (аналітика, діагностика треків) можна додавати без змін у виробнику.
- Відтворення подій після збою споживача; діагностика інцидентів.
- Вбудований буфер для пікових сплесків.

**Негативні / ризики:**
- Операційна складність (партиції, ребалансування споживачів, оновлення кластера). Мітигація: керований Kafka-сервіс або мінімальний кластер із 3 брокерів.
- Немає пріоритетів і TTL окремого повідомлення: протерміновану пропозицію водію (15 с) перевіряє споживач.
- Порядок гарантований лише в межах партиції; події, які залежать одна від одної, повинні мати однаковий ключ.
- Дублікати неминучі: кожен споживач зобов'язаний бути ідемпотентним.
