# ADR-004. Зберігання та пошук геолокації: Redis GEO + WebSocket push

- **Статус:** Accepted
- **Дата:** 2026-10-26

## Контекст

25 000 водіїв на лінії надсилають координати раз на 3 с (≈ 8 300 записів/с у пік). Матчинг має швидко відповідати на запит «вільні водії в радіусі R», а пасажир — бачити авто на мапі з оновленням не рідше ніж раз на 3 с. Дані швидко застарівають, а історія позицій для роботи системи не потрібна.

## Рушії рішення

- ASR-01 — p95 ≤ 2 с наскрізно (NFR-01); втрата окремих точок ≤ 1 % допустима, втрата водія з індексу — ні
- ASR-02 — масштабування в пік
- US-04 — позиція водія на мапі пасажира ≥ раз на 3 с
- US-15 — водій без зв'язку понад 60 с виключається з матчингу
- NFR-16 — клієнти втрачають зв'язок

## Розглянуті альтернативи

**Сховище і геопошук**

1. **PostgreSQL + PostGIS.** Багатий геоінструментарій, транзакційність. Але 8 300 оновлень/с по тих самих рядках створюють постійний write-amplification і навантажують основну БД; затримка запиту гірша, ніж у пам'яті; транзакційні гарантії тут не потрібні.
2. **Redis GEO.** Геоіндекс у пам'яті (`GEOADD`, `GEOSEARCH`), мікросекундні запити, горизонтальне шардування за містом. Мінус: дані в пам'яті, обмежений набір геооперацій.

**Доставка позиції пасажиру**

3. **Polling (REST раз на N с).** Просто, але у пік тисячі активних пасажирів × запит на 3 с — зайве навантаження на Gateway; затримка залежить від періоду опитування.
4. **WebSocket push.** Сервер надсилає позицію одразу після оновлення. Мінус: довгі з'єднання, ускладнене балансування.

## Рішення

- **Location Service (CT-08) володіє Redis GEO** (BC-03); Matching отримує кандидатів через gRPC `ILocationQuery`.
- Індекс шардується за містом. Redis GEO зберігає позиції в одному sorted set на місто, а TTL діє лише на ключ цілком, тож окрему точку прострочити не можна. Тому разом із `GEOADD` оновлюється **heartbeat-ключ водія** `driver:{id}:alive` з TTL 60 с. `nearbyDrivers` відкидає кандидатів без heartbeat, а фонове завдання раз на 30 с видаляє їх з індексу (`ZREM`). Позиція, не оновлена понад 60 с, виключає водія з пошуку (US-15).
- Потік від Driver App: WebSocket → Gateway → Location → `GEOADD` + публікація `driver.location.updated` у Kafka (ADR-003).
- Пасажир отримує позицію водія по WebSocket; Location підписаний на `driver.assigned` і `trip.status.changed`, щоб знати, кому слати.
- Індекс **не персистуємо як джерело істини**: водії повторно публікують позицію кожні 3 с, тож після падіння Redis індекс відновлюється за секунди.
- Геозона 200 м («Водій під'їжджає», T-08) обчислюється в Driver App.

## Наслідки

**Позитивні:**
- Затримка пошуку і оновлення на порядки менша, ніж у реляційній БД; основна БД не навантажується геопотоком.
- Push замість опитування: менше трафіку, швидше оновлення на мапі.
- Location масштабується незалежно (ASR-02).

**Негативні / ризики:**
- Після відмови Redis кілька секунд (до 3 с) індекс неповний. Матчинг у цей момент може не знайти водія і повторити запит. Мітигація: репліки з автоперемиканням, retry в Matching (INT-04).
- WebSocket-з'єднання зберігають стан: потрібні sticky-сесії або pub/sub між інстансами Location; при відновленні зв'язку можливий шквал перепідключень. Мітигація: випадкова затримка перепідключення у клієнті.
- Redis GEO не вміє складних геометрій (полігони зон, геофенси) — вони тут не потрібні; для звітів по тракам використовуємо потік Kafka.
- GPS-спуфінг не вирішується сховищем — розглядається в STRIDE (крок 9).
- Пам'ять Redis: ≈ 25 000 водіїв × малий запис — десятки мегабайтів, тож вартість несуттєва.
